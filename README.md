# Spendify

**Smart Spending, Student Style** — a budget and expense tracker built for college and
university students, on the MERN stack (MongoDB, Express, React, Node.js).

Students log income and expenses, categorise them, set monthly budgets, and read
plain-language summaries of where their money went. Administrators manage the default
categories, student accounts and system-wide notices from a separate control panel.

---

## Quick start

You need **Node.js 18+** and a **MongoDB** instance (a local `mongod`, or a free Atlas cluster).

```bash
# 1. API
cd server
npm install
cp .env.example .env          # edit MONGODB_URI if you are not on localhost
npm run seed                  # creates an admin and two demo students
npm start                     # http://localhost:5000

# 2. Front end (second terminal)
cd client
npm install
npm run dev                   # http://localhost:5173
```

Open <http://localhost:5173> and sign in with one of the accounts below.
The API automatically initializes the shared income and expense categories on its first start, so they are available to every student account.

## Deploy on Vercel (single root project)

This repository is configured to deploy the client and API together from the repository root.

1. Import the repository into Vercel and leave **Root Directory** set to the repository root (`.`).
2. Add these required environment variables in Vercel Project Settings for Production and Preview:
   - `MONGODB_URI` — your MongoDB Atlas connection string.
   - `JWT_SECRET` — a long, unique secret value.
3. Deploy. `vercel.json` installs both app packages, builds the client, serves `client/dist`, routes `/api/*` to the Express API, and sends browser routes to the React app.

The default build and install commands are configured in `vercel.json`. `CLIENT_URL` is optional on Vercel; the API allows the active Vercel deployment origin automatically. Add optional mail and AI environment variables in Vercel if those features are needed.

## How the "smart" parts work

Everything described as automatic is computed **locally from the student's own rows**, and
each piece is deterministic and can be explained line by line. The one exception is the
optional monthly summary: when `DEEPSEEK_API_KEY` is set in `server/.env`, the same figures
are sent to DeepSeek for a friendlier rewrite, and any failure falls back to the local
writer described below.

**Category suggestions** (`server/src/services/categorizer.js`)
A description is tokenised, then each candidate category scores:

```
score = 3 x (weights this student has taught us)  ...from the CategoryHint collection
      + 1 x (starter keyword matches)             ...from config/defaults.js
      + 0.5 x (the description names the category)
```

The top category wins if it clears a floor; confidence comes from its lead over the
runner-up and is capped at 0.95 so nothing is ever presented as certain. Every save
feeds back: the chosen category gains weight on each word, and a category the student
overrode loses some. That is what "learns from corrections" means here.

**Monthly insights** (`server/src/services/insights.js`)
Sentences are emitted only when the data supports them. The month is totalled, compared
against the three months before it per category, and checked against the budgets that
were set. Anything that grew more than 25% against the student's own average is named
with the figure, and the closing suggestion is tied to whatever was flagged.

**Saving tips** (`server/src/services/tips.js`)
Seven rules — categories running hot, budgets broken or nearly broken, the savings-goal
gap, subscription count, spending over income, many small purchases, and genuine
improvement. Each carries a `potentialSaving`, which is what the list is sorted by, so
the advice worth the most money is on top.

**Forecast and anomalies** (`server/src/services/analytics.js`)
The projection averages the last three months per category and adds half the
month-over-month slope (damped, because three points is little data). Anomaly detection
flags amounts above mean + 2 standard deviations for their category, and same-amount,
same-category entries within three days of each other.

Every generated suggestion in the UI carries a standing note that it is advice built
from the student's own entries, that it can be overridden, and that it is not certified
financial advice.

### Notes on the implementation

- **Charts are hand-built SVG** (`client/src/components/charts.jsx`) rather than a
  charting library, so the marks share the app's radii, type and both themes, and the
  bundle stays small. Donut, grouped bars, area line, ranked bars and sparkline.
- **Icons are hand-drawn paths** (`client/src/components/Icon.jsx`) on a 24×24 grid at a
  single stroke weight — no icon package.
- **Deleting a transaction is a soft delete.** The row keeps a `deletedAt` and stays out
  of reports, so "retaining the full history" is literally true and anything can be
  restored.
- **Budget alerts remember what they already sent**, so a student gets one warning per
  threshold per month rather than one per purchase.
- **Recurring entries catch up.** A rule stores its next run date; opening the app after
  two months away generates both missed entries, not one.

## Configuration

`server/.env`:

| Key | Purpose |
|---|---|
| `PORT` | API port (default 5000) |
| `MONGODB_URI` | Connection string |
| `JWT_SECRET` | **Change this before deploying** |
| `JWT_EXPIRES_IN` | Session length, default `7d` |
| `CLIENT_URL` | Allowed CORS origin and the base for password-reset links |
| `SMTP_*`, `MAIL_FROM` | Optional. Without them, password-reset links and shared reports are printed to the server console and the reset link is also returned in the response, so the flow stays testable locally. |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | The administrator created by `npm run seed` |
| `DEEPSEEK_API_KEY` | Optional. Enables the AI-written monthly summary. Blank means the summary is generated locally |
| `DEEPSEEK_MODEL` | Model id used for that summary, default `deepseek-chat` |
| `DEEPSEEK_BASE_URL` | Optional. Defaults to `https://api.deepseek.com` |
| `DEEPSEEK_THINKING` | `off` \| `on` \| `auto`. Thinking is on by default at the API and bills its chain of thought as output; this app ships with `off` |

## Deployment

```bash
cd client && npm run build      # produces client/dist
```

Serve `client/dist` as static files and run the API behind it, or host them separately
and point `CLIENT_URL` at the front end's origin. Set `NODE_ENV=production` and a real
`JWT_SECRET`.

## Security

Passwords are hashed with bcrypt. Sessions are stateless JWTs checked on every request,
and a disabled account is rejected at the middleware. Students and administrators are
separated by role at both the route and the UI level, and every student query is scoped
to the signed-in user's id, so one student's data is never reachable from another
account. Helmet sets the standard headers, CORS is restricted to configured origins plus local development and the active Vercel origin, and the
auth endpoints have their own tighter rate limit. The password-reset endpoint answers
identically whether or not the email exists, so it cannot be used to discover accounts,
and only a SHA-256 hash of the reset token is stored.

## Scope

Spendify does not connect to a bank, verify accounts or move real money. Every figure
comes from what the student typed in or imported from a CSV file.

## AI in the application

The only AI call in the product is the optional monthly summary. `services/ai.js` wraps
DeepSeek's OpenAI-compatible `/chat/completions` endpoint, configured entirely from
`server/.env`:

```
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_MODEL=deepseek-chat
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_THINKING=off
```

Thinking mode is switched off. DeepSeek enables it by default and returns the model's
chain of thought in `reasoning_content`, billed as output — on a short monthly summary
that was roughly five times the tokens and several extra seconds for no better text.
Set `DEEPSEEK_THINKING=on` if you would rather trade that back for deeper reasoning.

With no key the summary is written by the local template writer. With a key, the model
receives only that student's totals, top categories and budget outcomes, and anything that
goes wrong — missing key, timeout, refusal, a reply that is not usable JSON — falls back to
the local writer instead of failing the request. The key never leaves the server: it is
sent as an `Authorization` header, never in a URL, and is not exposed to the front end.

Categorisation, saving tips and forecasting remain rule-based and statistical, computed on
the project's own database. Claude (Anthropic) was used as a coding assistant while
building this project — for scaffolding, refactoring and reviewing code — and is not part
of the running application.
